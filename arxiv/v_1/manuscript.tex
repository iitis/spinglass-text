\begin{abstract}
This update consolidates \texttt{SpinGlassPEPS.jl}'s four separately registered
packages into one installable package with a defined public API. Truncating
factorizations now report relative discarded weight, an internal measure of
truncation loss for cold-started contractions. A new inverse-temperature ladder
can initialize later rungs from retained boundary matrix product states. On a
tested 2048-spin instance, warm starts reduced the two warmed rungs' wall times
by ${\approx}24$--$25\%$ and total ladder time by $\approx16\%$. Host work
dominated the profiled case. Moving contraction temporaries off the
garbage-collected heap reduced allocated memory for a 2048-spin bond-32 CPU solve
from 90.9 to 32~GiB. On the tested H100, GPU wall time was lower only for the
largest sparse case measured.
\end{abstract}

\section{Description of the software-update}
\label{Description of the software-update}

\subsection{Motivation and software consolidation}

The software described in the original publication~\cite{smierzchalski2025spinglasspeps}
consisted of separately registered Julia~\cite{bezanson2017julia} packages whose
version numbers were kept in sync. Their interfaces later diverged, and renamed
symbols lacked deprecation paths. The solver did not report truncation loss
during heuristic contraction, so users had no internal diagnostic without an
exact reference solution. The original benchmarks used CPLEX to certify ground
states. A separate study describes the algorithms and benchmark
campaign~\cite{dziubyna2025limitations}. Version 2.0.1 is archived on
Zenodo~\cite{spinglasspeps_zenodo}.

Version 2.0.1 consolidates the four implementation packages as internal modules
of one installable package, \texttt{SpinGlassPEPS}. These modules are
\texttt{SpinGlassTensors} and \texttt{SpinGlassNetworks}, together with
\texttt{SpinGlassExhaustive} and \texttt{SpinGlassEngine}.
\texttt{pkg> add SpinGlassPEPS} installs the complete solver.
The package exports about 80 documented symbols, compared with about 240
re-exported by the previous stack.
Lower-level kernels remain accessible through the submodules.

The clustered Hamiltonian now uses a concrete \texttt{PottsHamiltonian} with
typed fields and accessors instead of querying a \texttt{MetaGraphs} property bag
inside the search loop. Each contractor owns its cache of boundary MPS, MPO
layers and environments and evicts entries after each row. This replaces the
process-wide cache, which was not thread-safe and required manual clearing, and
permits concurrent solves.

\subsection{Correctness fixes and validation}

The update fixes two result-affecting defects. \texttt{corner\_matrix} failed
for every \texttt{SiteTensor} input and permuted the trailing dimensions of
\texttt{VirtualTensor} outputs. Tests against independent dense references now
cover both tensor types on CPU and GPU. The exhaustive GPU search launched too few
blocks and returned incomplete spectra for problems with at least ten spins. A
deterministic ten-spin regression test compares all 1024 GPU state codes and
energies produced by two 512-thread blocks against complete CPU enumeration.

The package now distributes the benchmark instances used for the original
article's figures. The published listing referenced a directory that was absent
from the distribution.

\subsection{Discarded-weight diagnostics and parameter selection}

Each truncating factorization records the relative weight it discards,
$\varepsilon_i = \lVert\Sigma_{\text{dropped}}\rVert_F^2/
\lVert\Sigma\rVert_F^2$, in a task-local accumulator. This prevents concurrent
solves from mixing statistics. A solve reports $\sum_i\varepsilon_i$ and
$\max_i\varepsilon_i$. It also reports the number of truncations for which the
bond-dimension bound, rather than the singular-value tolerance, caused a
non-negligible discard and the number of retained dimensions out of those
offered. The original release reported neither of the latter quantities. On a
128-spin instance, bond dimension $D=4$ gives $\sum\varepsilon =
3.1\times10^{-4}$ with all 18 truncations forced by the bond bound, retaining
108 of 307 singular values. At $D=32$ the same solve gives $5.6\times10^{-14}$,
with none of its four recorded truncations bond-limited, retaining 192 of 592
singular values. A bond-limited count of zero means that no bond-capped
truncation discarded relative weight above the $10^{-12}$ reporting threshold.
For this cold contraction, the diagnostic does not indicate a need to increase
$D$ at the reported precision.

For an eight-transformation sweep, the solver reports the energy range and the
number of transformations that attain the minimum. Agreement across the eight
contraction orders provides a consistency check without a reference solution.
The relative energy range measures sensitivity to contraction order, which can
arise from contraction or search error.

The inverse temperature $\beta$ controls how strongly the conditional branch
probabilities favor low-energy states. At small $\beta$, these probabilities
contain little information about the ground state. The original interface
accepted one $\beta$ value, although its documentation noted that the best value
depends on the instance. The update adds \texttt{beta\_ladder}, which evaluates an
increasing schedule. When a retained boundary MPS has the physical dimensions
required by the next rung, that rung uses it to initialize variational
compression instead of forming $W\psi$ exactly and truncating it. On the tested
2048-spin instance, where
boundary-MPS construction dominates, warm starting reduced the two warmed rungs'
wall times by about 24\% and 25\% relative to independent cold builds, with
identical energies. Median paired cold/warm time ratios were $1.32$ and $1.34$
over five interleaved rounds.
Because the first rung is cold in both protocols, the reduction over the full
ladder was about 16\%. The speedup depends on the fraction of runtime spent
constructing boundary MPS and is smaller when search dominates.

For a cold ladder, a completed rung is marked trusted when its accumulated
discarded weight satisfies $\sum_i\varepsilon_i \leq \texttt{max\_discarded}$.
The routine selects the minimum-energy trusted rung. If no trusted rung has a
valid energy, it returns the minimum-energy successful rung as a fallback and
leaves it flagged as untrusted. The threshold acts as a preference filter,
not a hard acceptance criterion. Setting \texttt{stop\_when\_untrusted=true}
terminates the ladder after the first successfully completed rung above the
threshold. This can reduce cost, but it may miss a later acceptable or
lower-energy rung because discarded weight is not monotone in $\beta$.

The discarded-weight diagnostic does not measure warm-start error. A warm start
optimizes within a fixed bond dimension without a truncating factorization, so
it can report $\sum\varepsilon\approx0$ despite a nonzero variational gap. The
package warns when \texttt{max\_discarded} is used with a warm start. Discarded
weight also does not rank solution quality. In
Figure~\ref{fig:evr}(c) the median energy error decreases to zero by $\beta=6$,
where 9 of 10 instances reach the best energy found. The median
$\sum\varepsilon$ peaks at $\beta=4$ and then falls, because a sharply peaked
Boltzmann distribution carries less entanglement and truncates more easily. At
$\beta=2$, the median $\sum\varepsilon$ was near its minimum but the median
energy error was largest. At $\beta=4$, the median $\sum\varepsilon$ was largest
and the median energy error was smaller.

At $M=1024$, 49 of 50 instance-temperature runs remained within one valley under
the $N/4$ criterion after quotienting the exact global spin-flip symmetry
(Figure~\ref{fig:evr}(d)). For four of five instances, the eight lattice
transformations produced states in two or three valleys. The maximum pairwise
quotient distance was 1249, compared with the maximum possible value of 1250.
Across the five instances, the relative energy spread remained between
$2.21\times10^{-4}$ and $5.74\times10^{-4}$.
Supplementary Section~\ref{sec:supp-diversity} reports distance quantiles for
each run, transformation results for each instance and the exceptional
$\beta=8$ run.

\subsection{Transformation sweeps and hardware performance}

The standard protocol applies each lattice transformation once per instance.
Previously, users implemented this loop themselves. \texttt{sweep\_transformations}
seeds each transformation deterministically because \texttt{Zipper} draws a
random sketch and task scheduling can otherwise affect results. A failure in one
transformation does not abort the others, and each result includes the
diagnostics described above. Available device memory limits concurrency. A
calibration solve estimates peak memory. The sweep then admits tasks within a
byte budget and assigns each task a local reservation for sizing kernel batches.
This prevents concurrent tasks from each assuming access to the full memory
pool.

Concurrent execution reduced sweep time on both CPU and GPU
(Table~\ref{tab:sweep}). CPU speed-up increased with $c$, reaching $3.1\times$
and $1.6\times$ for the 36- and 128-spin cases at $c=8$. Among the measured GPU
settings, the highest speed-ups were $1.7\times$ for the first case at $c=2$ and
$1.4\times$ for the second at $c=4$.
With $c=1$, setup overhead made the sweep slower because no solves overlapped.
Serial and concurrent runs returned identical energies for every configuration.
Ratios follow the paired, interleaved protocol described in the table caption
and Supplementary Section~\ref{sec:supp-timing}.

\subsection{Profiling and allocation}

On a profiled 128-spin solve, host-side CUDA API calls occupied 27.0\% of the
profiled interval and GPU activities occupied 6.6\%. Because these intervals may
overlap, at least 66.5\% lay outside both categories. The low GPU-activity share
is consistent with the crossover results because faster tensor kernels cannot
reduce host-side work.

Kernel-level batching could reduce device idle time, but eliminating the entire
measured CUDA API interval would still cap the Amdahl speed-up at about
$1.4\times$. We focused instead on host allocation. In the pre-change
implementation, \texttt{branch\_states} accounted for 52.7\% of the bytes
allocated by a 128-spin solve. A single matrix now stores branched configurations
instead of tens of thousands of small vectors per call
(Figure~\ref{fig:alloc}). In the 2048-spin, bond-32 case, this reduced allocated
bytes by about 4\% on GPU and 1\% on CPU, while primarily reducing the live-object
count. Multi-tensor contraction temporaries were also moved off the
garbage-collected heap. For the corresponding CPU solve, allocated bytes fell
from 90.9 to 32~GiB, a reduction of about two thirds. Both changes were measured
in full solves. The explicit allocator was not faster in isolation. Its benefit
is reduced garbage-collected allocation.

\subsection{Impact and limitations}

For instances without a known optimum, the discarded-weight diagnostic reports
accumulated loss from cold-contraction truncations. The consolidated
package defines one public API, and deprecation shims preserve renamed entry
points. Bundling the benchmark instances makes the reported runs reproducible.
Supplementary Section~\ref{sec:supp-reproducibility} maps the additional results
to their drivers and committed records. The companion article repository
contains the raw per-run data, figure scripts and runnable drivers. The
pre-change values in Figure~\ref{fig:alloc} are recorded measurements from the
superseded implementation.

Warm starts currently retain only the bottom-boundary MPS. Rows contracted from
the top cannot reuse it. In our tests, $\sum\varepsilon$ did not identify the
$\beta$ yielding the lowest energy reliably, so the package documents it as a
diagnostic rather than a selection criterion.

\section{Solution-diversity analysis}
\label{sec:supp-diversity}

The diversity experiments used 2500-spin square-lattice instances without local
fields, so every state $\sigma$ and its global spin flip $-\sigma$ have exactly
the same energy. To avoid counting this symmetry-related pair as two valleys,
distances are reported as
\[
    d_{\mathbb{Z}_2}(\sigma,\tau)
    = \min\!\left(d_H(\sigma,\tau),N-d_H(\sigma,\tau)\right),
\]
where $d_H$ is Hamming distance and $N=2500$. The largest possible quotient
distance is $N/2=1250$. The diversity criterion used in the original article is
$N/4=625$.

Of the 50 instance-temperature runs tested at \texttt{max\_states}=1024, 49
remained within one valley. Across those runs, the largest quotient distance
between any returned state and the best returned state was 399. The sole
exception was instance 1 at $\beta=8$. Its best returned energy was 8.12 above
the lowest energy among the five fixed-order $\beta$ runs for that instance. No
returned state was the global spin flip of the best returned state. We interpret
this result as a degraded contraction rather than evidence of an additional
low-energy valley.

Varying the contraction order broadened the solution set. At $\beta=4$,
selecting one state from each of the eight lattice transformations yielded two
or three distinct valleys on four of five instances. Pairwise quotient distances
reached 1249, compared with the maximum possible value of 1250. Across the same
transformations, the relative energy spread ranged from $2.21\times10^{-4}$ to
$5.74\times10^{-4}$.

The per-run distance quantiles are stored in \suppfile{div3.csv} and
\suppfile{div3_extra.csv}. The per-instance cross-transformation measurements
are in \suppfile{xtransform.csv}. Panel (d) of Figure~1 in the main article
reports medians over ten instances of the 50th, 90th, and 100th within-run
distance percentiles. At $\beta=4$, the square marks the median across five
transformation-sweep instances of the pairwise median distance. Its error bars
extend to the corresponding medians of the pairwise minimum and maximum.

\section{Timing protocol and CUDA memory-pool artifact}
\label{sec:supp-timing}

\subsection{Paired measurements}

The concurrent-sweep and inverse-temperature-ladder comparisons use paired
measurements. The two arms are interleaved within each round. The concurrency
driver performs a full \texttt{GC.gc(true)} before each timed section, followed
by \texttt{CUDA.reclaim()} for device measurements. The ladder driver performs
the same host reclamation before each complete cold or warm arm. Reported
speed-ups are medians of the per-round paired ratios.

The ladder benchmark used the 2048-spin sparse instance at $D=16$ with five
rounds and seeds 2 through 6. Each round ran one cold and one warm ladder on
fresh contractors. Their order alternated across rounds. Rung 1 was cold in
both arms. Rungs 2 and 3 reused a retained boundary MPS only in the warm arm.
Table~\ref{tab:supp-ladder} reports the paired timing ratios. Median discarded
weights for the cold arm were $3.203543\times10^{-3}$,
$1.686507\times10^{-4}$, and $1.856007\times10^{-5}$ over the three rungs. The
warm arm matched the first value and recorded zero for rungs 2 and 3 because a
warm start does not perform a truncating factorization. The returned rung
energies were $-3334.080055$, $-3336.773383$, and $-3336.773383$.

\subsection{Timing contamination checks}

A misleading result from a sequential protocol motivated the paired design. We
retained its summary values, but not the raw development log. A concurrent
warm-up left the CUDA memory pool in a different state when the serial arm was
timed.
For identical work, the serial baseline rose from 14.3~s to 38.8~s, a factor of
approximately 2.7. The contaminated baseline implied a speed-up of
$1.68\times$, whereas the corrected paired protocol gave $0.92\times$. All
reported sweep and ladder ratios use the interleaved protocol and reclamation
steps above.

The crossover experiment uses alternating separate processes. Each process
receives an uncontended device, and the summary uses the minimum of its repeated
wall-time measurements. Timing runs were performed on an otherwise idle
machine.

An exploratory benchmark run coincided with the full package test suite and
returned a different energy at one of 30 benchmark points. We excluded that run
because the machine was not idle. The cause of the difference remains unresolved.

\section{Correctness regression coverage}
\label{sec:supp-correctness}

The two result-affecting defects described in the article are covered by
dedicated regression tests. Tests in
\path{test/tensors/contractions_site.jl} and
\path{test/tensors/contractions_virtual.jl} compare
\texttt{corner\_matrix} outputs with independently constructed dense references.
They verify output dimensions and numerical values on CPU and GPU.

The exhaustive-search regression in \path{test/exhaustive/ising.jl} uses a
deterministic ten-spin instance. It compares all 1024 GPU state codes and their
energies with complete CPU enumeration. The GPU launch uses 512 threads per
block, so this test exercises two blocks and crosses the boundary that exposed
the former incomplete-spectrum defect. GPU regression tests run when CUDA is
functional. CPU test groups remain available on systems without a CUDA-capable
device.
